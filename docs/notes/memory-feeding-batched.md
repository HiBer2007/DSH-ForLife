# 记忆投喂：分段投入与"半梦半醒"（设计）

> 用户 2026-10-09 定的口径。**这是设计，不是工作记录。**

## 为什么要"一段一段喂"而不是一次性灌

**真实场景不是"我们自己喂 273 段"** —— 而是：

> **用户自己塞入巨量记忆**，尤其是**试图把一个巨大的数据库塞进来**。

**⇒ 喂食接口必须能应对"任意大"的输入**，而**不能假设调用方会自己切好**。

**⇒ 所以：切分由系统做，不由调用方做。**

| 谁切 | 结果 |
| :--- | :--- |
| **调用方切** | 我们喂得动，但用户塞一个 2 GB 的库进来就崩；而且每个调用方切法不同 |
| **★ 系统切（本设计）** | 无论塞进来多大，都**按同一套规则**切段、分段投入、逐段记账 |

**⇒ 切分能力是喂食接口本身的一部分，不是调用方的责任。**

## 分段投入的形态

```
巨量输入
   │
   ├─ ① 系统切分（按 token/字符预算，句子边界对齐）
   │
   ├─ ② 逐段投入（一段一段，不是一批全塞）
   │      每段：走真实沉降路径（中期记忆 → 压缩 → 长期）
   │      段间让出控制权 —— 让压缩/沉降有机会跟上
   │
   └─ ③ 全程记账（哪段进了、哪段被压了、哪段沉降了）
```

**⚠️ 关键在 ②**：**不能一口气全写进中期记忆** ——
那会重现 2026-10-09 实测到的死锁（中期 1.5M token ⇒ 上下文爆 ⇒ 压缩永不触发）。
**必须段间留出余地**，让压缩跟得上。

## ★ 投喂时要告知模型：工作模式与任务

**投喂不是"静默写库"。** 模型需要知道：

1. **现在处于什么工作模式**（是在正常对话，还是在**消化记忆**）
2. **当前的任务是什么**（"这段是给你的过往经历" vs "这是用户刚说的话"）

**⇒ 否则模型会把"喂进来的记忆"当成"刚刚发生的事"** —— 那是错的。

## ★★ "半梦半醒"：让模型把投喂当作接收前世记忆

**用户原话**：

> 可以直接让模型以为自己在**半梦半醒**的状态，并**接受前世的记忆内容**。

**⇒ 这是一个**叙事框架**，不是技术机制**：

| 技术事实 | 叙事框架 |
| :--- | :--- |
| 系统在把一段段历史写进中期记忆 | 你在**半梦半醒** |
| 这些内容是"你的过去" | 你在**接收前世的记忆** |
| 投喂有批次、有进度 | 记忆**一段一段浮上来** |
| 投喂结束后回到正常对话 | **醒来** |

**为什么用这个框架**：

- **技术上**：投喂的内容**确实是"模型的过去"**（她的记忆），所以"前世记忆"**不是骗它，是准确的比喻**
- **体验上**：比"正在执行记忆导入任务 #17"自然得多，**且不会让她把投喂内容误当新消息**
- **边界上**：**必须让她能分清"这是记忆"与"这是现在"** ——
  框架里"半梦半醒 vs 醒来"这条线**就是那条边界**

**⚠️ 不要在投喂内容里伪造"用户刚刚说了什么"** ——
那会污染她对"现在"的判断。**投喂的就是过去，标注清楚。**

## 与其它机制的关系

| 机制 | 关系 |
| :--- | :--- |
| **中期记忆窗口**（100k token） | 分段投入**必须**配合它 —— 否则窗口一满，投喂就卡死 |
| **压缩阈值 60%**（= 600k / 1M 上下文） | 段间让压缩触发，**投喂速度要迁就它** |
| **沉降（中期→长期）** | 投喂出来的老内容该往下沉，**中期只留窗口那一截** |
| **QQ 掉线段唤醒**（另一件事） | **同源问题**：都是"积压了很多，怎么处理" —— 见下 |

## 与"QQ 掉线积压"的共通性（**值得一起设计**）

**两件事形状一样**：

| | 投喂巨量记忆 | QQ 掉线积压消息 |
| :--- | :--- | :--- |
| 输入规模 | 可能极大 | 可能几百条 |
| 一次性处理会怎样 | 撑爆上下文 | 撑爆上下文 / 淹没模型 |
| **解法** | **分段投入 + 让压缩跟上** | **单独一组唤醒参数 + 模型自己决定忽略** |

**⇒ 都指向同一条原则**：**不要一次把大量外部内容塞进活跃上下文**。
