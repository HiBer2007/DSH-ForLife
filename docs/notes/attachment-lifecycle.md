# 附件的生命周期：删除留回忆 vs 作为条目附件保留（设计）

> 用户 2026-10-09 提的硬要求。**这是设计，不是工作记录。**

## 用户原话

> 由于附件等等往往会很多，我们必须在提供时
> （**包括 QQ 下载的图片/文件、投喂记忆的时候的附件**）
> 让模型**直接抉择好**到底是：
> - **到中期记忆/长期记忆后删除原始文件留下回忆与碎片**，**或者**
> - **选择作为中期记忆/长期记忆条目的附件保留**

## 要解决的问题

**附件的体量与正文不是一个量级**：

| | 正文（消息） | 附件（图片/文件） |
| :--- | :--- | :--- |
| 单个大小 | 几 KB | **几十 KB ~ 几十 MB** |
| 数量 | 与对话条数同阶 | ★ **可能极多**（截图、表情、随手拍） |
| 价值 | 高（语义） | **极不均**（有的关键，有的看完就没用） |

**⇒ 所以不能"一律保留"**（存储会爆），**也不能"一律删"**（会丢掉真正重要的东西）。**
**⇒ 只能**逐条判断**，而**只有模型有判断所需的语境**（她知道那张图重不重要）。**

## 所以设计成两条路，由模型选

| 选择 | 行为 | 代价 / 收益 |
| :--- | :--- | :--- |
| **① 删除留回忆** | **删掉原始文件**，条目里只留：<br>· **文件名与元数据**（时间、类型、尺寸）<br>· **模型写下的"这是什么"**（描述/回忆）<br>· **碎片索引**（可检索的钩子） | 省存储；**但原件不可恢复** |
| **② 作为条目附件保留** | 原件**挂到中期/长期条目上**（`media_assets` 那类），**随条目一起沉降** | 占存储；**但随时可回看原图** |

**★ 关键：这个选择要落在**条目**上（每条自己的附件各自决定），不是全局开关。**

## 两个来源都要走这条路

**用户明确点了两处**：

1. **QQ 下载的图片/文件** —— 别人（或她自己）发进对话的
2. **投喂记忆时的附件** —— 例如本次那 **163 个**（华为健康截图 / 照片 / PLAN.MD / 统计报告）

**⇒ 两条路的实现可以是同一个机制**（都是"把附件挂到某条记忆上"），
**但入口不同**（一个是 QQ 消息流，一个是投喂管线）。

## 与本次网页端导出的关系（**说清楚，免得误会**）

**本次从 DeepSeek 导出的 JSON里**没有图片本体**，只有元数据**：
```
file_name / model_kind / is_image / width / height / file_size
```
**⇒ 所以那 163 个附件现在**只留下了文件名与尺寸**，**并没有下载任何文件**。**

**文件名本身信息量不小**（例）：
```
screenshot_20261004_093858_com.huawei.hmos.health_4626108343866024194.webp   1128×2444
IMG_20261004_102229_2662501187554848250.webp                                 1536×2048
PLAN.MD                                                                      22190 字节
统计报告-2026-10-01-1828.md                                                   5330 字节
```
**⇒ 时间 + App + 是截图还是拍照**，本身就是可用的记忆线索。
**⇒ 这属于上面 ① 的"删除留回忆"形态**（原件没拿到，但有元数据 + 可写描述）。

**若要拿原件**，得另找来源（网页端有没有文件下载地址 / QQ 侧 `media_assets`）——
**那是另一件事，不阻塞这里。**

## 与"分段投入"的关系

**附件往往是"量大"的主因**（一次投喂可能带几百张图）。
**⇒ 所以附件处理必须和「分段投入」一起做**：
- 投喂时**分段**，每段里的附件**逐条**让模型决定去留
- **不要**在切分阶段就把附件全读进内存（那正是"塞一个巨大数据库"的场景）

## 待定（**要用户拍板**）

| # | 问题 |
| :--- | :--- |
| **1** | **② 保留**时，原件放哪？中期记忆是上下文的一部分，**附件不该进提示词** —— 那它该挂 `media_assets` 还是别的表？ |
| **2** | **① 删除**后，**"回忆"由谁写**？模型自己写描述（一次调用），还是投喂时一并生成？ |
| **3** | **能不能反悔**？① 删了就没了 —— 要不要先"冷藏 N 天"再真删？ |
| **4** | **默认值**是什么？（我倾向：**默认 ①（删原件留元数据+描述）**，因为存储是硬约束；模型可显式选 ②） |
| **5** | 配额：**② 保留**要不要总量上限（比如全局 2 GB），超了强制走 ①？ |
